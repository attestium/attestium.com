# Introduction

[Attestium](https://github.com/attestium/attestium.com) is an open-source library and an open evidence format for **remote attestation of what a server runs**. Its purpose is narrow: to let a third party check, without trusting the operator, that a service runs the open-source code it has published. The check covers the service's own files, every package it installs from a registry, the language runtime that executes it, the executables and shared libraries its processes map, and the containers it runs in. It applies to any language and to any binary, because every file that runs is either explained by a public reference the operator does not control or reported as unexplained.

The SolarWinds [@solarwinds] and xz-utils [@xz_utils] compromises showed how much damage a change to shipped code can do before anyone notices. The industry has responded mainly at build time, with signed artifacts, provenance and hardened build pipelines [@slsa; @sigstore]. These are necessary, but they end at deployment. Once code is on a server, a user of the service has no way to know whether it is the code that was built, reviewed and published. Sonatype's annual report counted more than 245,000 malicious open-source packages in a single year [@sonatype], and nothing in a typical deployment checks the installed files against what a lockfile pinned.

System Transparency, developed for Mullvad's VPN servers, showed that verifiable infrastructure is possible at the level of the boot chain [@mullvad_st; @mullvad_diskless]. Attestium applies the same idea to the running application: the files it loads, the executable bytes mapped into its processes, and the upstream releases its runtime and dependencies came from. Executive Order 14028 [@eo_14028] and the NIST Secure Software Development Framework [@nist_ssdf] both call for stronger assurance about the software in use; Attestium is a building block for that assurance.

The design follows the IETF Remote ATtestation procedureS (RATS) architecture [@rats]. An **attester** on the audited machine collects facts and never judges them. A **verifier** elsewhere sends a fresh nonce, receives the evidence, and compares every fact with a reference it obtains itself: a public commit, a reproduced build, a registry package pinned by a lockfile, a container image by digest, an official runtime release, a signed checksum list, or a package from a distribution's signed archive. **Relying parties**, such as the users of a service, read the verifier's results. Where the machine has a TPM 2.0 [@tpm2_spec] or runs as a confidential virtual machine (AMD SEV-SNP [@sev_snp] or Intel TDX [@tdx]), the evidence is bound to hardware-signed statements, and each result states which level of evidence it reached.

[Audit Status](https://github.com/auditstatus/auditstatus.com) is a separate project built on Attestium: a ready-made attester and verifier, with deployment tooling for servers and Kubernetes clusters and a GitHub Action that publishes results. Attestium defines what evidence is and how each part of it is checked; Audit Status runs those checks for a fleet and publishes the outcome. Forward Email uses both to publish, on its status page, whether its production servers run the code in its public repository.
